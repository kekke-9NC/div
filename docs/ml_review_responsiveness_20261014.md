# 旧UIの目視レビューボタン応答改善（2026-10-14）

## 原因

添付画像の「未確認データを目視レビュー」は、GUI側で確定済みデータのメディア整理を完了してから画面を開いていた。現データは未確認1,126件、確定済み7,710件、スキップ6件、review_log.jsonlは30,937,063バイト。画面を開く際に判定・スキップ履歴をコンストラクタとrefreshでそれぞれ読み、合計4回JSONLを走査していた。データ増加によってクリックから表示までの待ちも増える構造で、解析高速化変更そのものがこの遅延を生んだとする比較測定はない。

## 修正

- レビュー画面を先に作成し、確定済みメディア整理・未確認一覧・履歴読込みを専用workerへ移した。Tk操作はGUI側の50ms queue pollだけで行う。
- 判定・スキップ履歴を1回の走査で取得。起動時の履歴走査は4回から1回（この部分の読み込み量は約124MBから約31MB）。表示応答時間が4倍になるという意味ではない。
- 読み込み中の判定・取り消し・一括操作を止め、完了後に履歴と操作を復元する。読み込み失敗時も古い取り消し履歴で操作しない。
- 連打は既存画面を再利用。異なる保存先への切替は現在の整理処理が終了してから開く。最新の再表示要求だけを保持する。
- 閉じる操作はイベント単位でcancelする。動画・画像移動とmetadata/log更新は元のトランザクションを完了またはロールバックし、途中で打ち切らない。workerはTkを呼ばず、親画面の破棄時もcancelする。
- 既存metadataに記録されたメディア保存先は従来通り尊重する。設定の変更を過去のファイルの一括移動として解釈しない。
