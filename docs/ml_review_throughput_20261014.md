# 目視レビュー・一括選別の追加改善（2026-10-14）

## 調査

v0.10.14.5では画面を先に表示したが、検索後も履歴全件の再読み込み、選別後も全体の再走査が残っていた。個別の確定・スキップ・取り消しの保存処理もGUI上で実行していた。

実データの診断時点では、review_log.jsonlは31,639,468バイト。review 8,023件、skip 51,924件、undo 78件、undo_skip 52件、既存メディア同期55件。存在するデータは未確認253件、確定7,945件、スキップ644件だった。古いログには既に移動・削除されている保存先が多数あり、履歴復元で毎回約6万件のPath.existsを呼ぶ構造になっていた。分類変更では、流星15,128ファイル・非流星7,306ファイルのフォルダを1イベントごとに走査し、すべてのファイルにis_fileを呼んでいた。

OSの旧アプリsampleにはTk/QuartzCoreの画像描画負荷も見られた。これは操作ごとの所要時間を測ったものではない。

## 変更

- 検索はデータを変更しないため、完了後に履歴・プレビューを再読み込みしない。
- 正常な一括処理は戻り値の確定済みレコードだけで判定履歴を更新し、未確認フォルダだけを読み直す。検索後にデータ変更が検出された場合や処理失敗時は、整合性を優先して履歴も再読み込みする。
- 個別の確定・スキップ・取り消し・同一日検索をworkerへ移し、Tk更新はGUI側のqueue pollに限定する。正常な個別確定・スキップは処理済みイベントだけを一覧から取り除き、全未確認一覧も再走査しない。
- 履歴はファイルのdev/inode/size/mtime/ctimeが一致する場合に解析結果を再利用。存在確認は保存先の親フォルダをまとめて列挙し、レコードごとのstatを避ける。取り消し照合はtimestampの索引で行い、重複timestampでも最後の有効なレコードを取り消す。
- 保存メディアは更新時刻付きのファイル名索引で対象prefixを絞り、該当するファイルだけにis_fileを呼ぶ。元の一致条件（同名・同stem・prefixに続くunderscore）を保持し、フォルダ更新時は索引を作り直す。
- 検索のmetadataはファイル属性が一致する場合に再利用。実際の選別前には毎回原本を読み直し、検索時のSHA256と照合する。
- 確定済みデータの同期は変更されていない、同期対象外または同期済みのmetadataを再解析しない。同期対象だが動画がまだ見つからないイベントは再確認する。
- 動画プレビューのTk画像を使い回し、毎フレームの画像再作成・widget再設定を省く。プレビューのフレーム間引きは加えていない。検索だけなら開いている動画を再利用して再生を再開する。
- 一括進捗表示をpollごとにまとめる。保存workerは画面破棄時にcancelし、進行中のファイル移動は完了またはロールバックしてから終了する。

取り消し先が既に存在する場合は元の判定を未取り消しとして履歴に残す。監査で見つかった、こうした競合時にローカル履歴から消える問題を修正した。ファイル移動・metadata更新・ログfsync・ロールバックの既存処理は維持した。
