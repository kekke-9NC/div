# 短い流星の検出改良：処理時間の比較（2026-10-11）

旧UIの改良前の処理実装と、コミット `ac085be` の改良後の実装を、同じ元録画・マスク・分類モデルで比較した。
改良前は修正直前に保存した `video_processing.py` を読み込んだ。

## 条件

- 全6本とも1920×1080、25fps、1500フレーム＝60秒の録画。日時はJST。
- 曇天プリセット、旧UIの保存済み検出マスク、meteor_event_transformer_boost_v1を共通使用。
- 分類の判定しきい値は0.8822220810862557。
- 配信中の負荷を抑えるため、CPUのみ、低優先度、ネイティブ処理1スレッド、詳細検出2ワーカー、デコード1スレッドで順次実行。
- 動画の読み込み・候補検出・詳細検出・分類・検出情報の作成を計時。モデル初期読み込み・初回ウォームアップ、結果動画の書き出し、学習データ保存は除外。通知なし。
- 夜間4本は改良前後各2回。実行順をABBA／BAABと入れ替え、表は平均。
- 明るい夕方・明け方は各1回。長時間の負荷を避けるため180秒で未完了の処理を終了した。
- アプリ、OBS、ライブカメラは再起動せず、実運用の設定も変更していない。

## 時間が増える理由

追加した元解像度の背景差・光点追跡を各フレームに対して実行する時間が増える。
さらに、これまで詳細検出で落ちていた短い候補が分類器へ進むため、候補の多い動画ほど分類の時間も増える。
20:30の動画は分類器への入力が改良前0件、改良後35件。23:30は両方0件で、追加の分類がない場合でも追跡処理の分だけ約8秒増えた。

夕方17:50の動画は、改良前は全60秒を処理して分類0件。改良後は180秒で未完了となり、その時点でログの解析窓は176〜200フレーム（冒頭約8秒）まで、分類の出力は391件あった。
明るい空のノイズを追加の候補経路で大量に拾ったことが、負荷増加の主因と考えられる。暗い録画だけで確認した前回の検証ではこの問題は分からなかった。
明るい時間帯は候補のノイズ対策が必要で、この測定条件では録画速度に追いつかない。

## 解釈の限界

- CPUを制限した同条件の比較であり、GPUや多スレッドを使う普段の旧UIの所要時間をそのまま示すものではない。結果動画の保存時間も含まない。
- 同じ時間帯でも雲、ノイズ、候補数、ほかの処理の負荷により所要時間は変わる。各時間帯の全動画を代表する保証はない。
- 180秒超は打ち切りの下限で、完了までの時間は測定していない。途中の進行率から完了時間を推定していない。
- 分類器の出力件数は処理量の指標。今回の動画全体について流星の正解個数を作成した精度評価ではない。
